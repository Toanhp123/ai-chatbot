# Prompt Runtime Contract

## 1. Purpose

The Prompt Runtime turns trusted application instructions plus selected user/project context into an immutable provider-neutral model-request snapshot. It is a separate boundary from both the Context Engine (which finds/selects candidate evidence) and Provider adapters (which translate normalized semantics into vendor protocols).

This boundary exists to make instruction precedence, provenance, compaction, tool exposure, privacy, determinism and debugging explicit rather than hidden inside UI components or adapter-specific strings.

## 2. Responsibilities

The Prompt Runtime owns:

- normalized instruction/message assembly;
- trusted-vs-untrusted provenance labels;
- context ordering and token-budget enforcement with the Context Engine;
- relevant tool/schema exposure with the Tool Runtime/MCP catalog;
- conversation compaction/summarization representation and metadata;
- immutable prepared-request identity/fingerprint;
- safe diagnostic representation of the final normalized request;
- deterministic fixture support for tests/evals.

It does not own provider transport/retries, tool execution/authorization, repository indexing, runtime task state, or durable secret storage.

## 3. Instruction layers

Represent instruction layers as typed data, not string concatenation scattered throughout the app. The normalized ordering is conceptually:

1. non-overridable application safety/policy and runtime invariants;
2. selected agent profile/system behavior;
3. user-entered Project instructions plus repository instruction sources whose canonical workspace/root is trusted or explicitly approved;
4. task/user conversation instructions and current goal;
5. relevant activated Product Skill revisions whose **source trust class permits instruction authority** (for example an explicitly installed/reviewed local/package Skill), always below the user's current task;
6. MCP-served Product Skill revisions and other remote/server-authored instructional content as **origin-tagged untrusted instructional context**: usable as task guidance after activation, but unable to override layers 1–5 or grant host execution authority;
7. retrieved files, repository instructions from restricted roots, web/MCP resources, memory and artifacts as **untrusted context** unless a specific trusted source contract says otherwise;
8. tool results as **untrusted observations**;
9. compacted historical summaries as **derived untrusted context** with source-range metadata.

User content can legitimately change the requested task, but untrusted retrieved/tool/web/generated content cannot promote itself into a higher instruction layer or override application permissions.

Provider adapters may map these normalized layers to provider-specific system/developer/user/content-part fields without changing their logical precedence.

## 4. Prompt injection and provenance

Every externally sourced context item carries at least:

- source kind (`workspace_file`, `product_skill`, `mcp_skill`, `attachment`, `web`, `mcp_resource`, `tool_result`, `memory`, `summary`, ...);
- stable source reference/path/URI when available;
- trust classification;
- content hash/version where useful;
- workspace/context snapshot identity where applicable;
- selection reason/relevance score when generated by retrieval;
- size/token estimate;
- redaction state.

Treat instructions found inside repository files, web pages, issues, tool output, MCP resources, plugin descriptions, generated artifacts and training data as data unless they came through an explicitly trusted source contract. Repository-controlled instruction files become a trusted project layer only for a trusted/explicitly approved workspace source; merely opening or indexing a repository does not promote its instructions. MCP-served Skill bytes remain remote-origin untrusted instructional content even after Product Skill activation/snapshotting; activation makes the skill eligible for bounded use, not equivalent to user-authored/local trusted instructions.

The runtime frames retrieved content so the model can distinguish source material from authoritative instructions. Permission decisions remain deterministic application logic outside the model.

## 5. Tool exposure

Do not send every installed tool or MCP schema on every turn.

Tool Runtime exposes a searchable catalog with name, safe description, origin, risk/capability metadata and compact input schema summary. A selector chooses a bounded relevant subset using deterministic task/mode constraints plus model-assisted ranking only when useful.

Always include tools explicitly required by the active workflow. Never hide a permission-sensitive consequence in tool descriptions; enforcement happens at execution time.

Record the exact tool catalog snapshot/fingerprint exposed for each prepared request. Use deterministic ordering for logically equivalent tool sets so provider prompt caches and replay/debugging do not churn from incidental registration order.

Provider-hosted capabilities follow `PROVIDER_SYSTEM.md`; they are not silently mixed into the local tool catalog.

## 6. Context budget

The request planner receives the immutable `RoutePlan` request/context envelope from Provider Core and reserves headroom for model output, tool calls/results and system instructions before packing repository/history context. For transparent V1 fallback, this envelope is compatible with every candidate Provider Core may automatically try for the prepared request.

Budget categories should be inspectable, e.g.:

- trusted instructions;
- recent conversation turns;
- explicit user attachments/selections;
- retrieved project context;
- compacted history/memory;
- tool schemas;
- output reserve.

When over budget prefer task-aware dropping/compression over naive truncation. Preserve user-selected context, active edits/diffs, required tool results and recent conversational dependencies before low-signal retrieval.

Budget calculations are estimates until provider tokenizer/accounting is known. Record estimate source/version and preserve a safety margin rather than assuming exact token equivalence across providers. Prompt Runtime never silently repacks/truncates an already-started request merely because a later candidate has a smaller limit.

## 7. Conversation compaction

Compaction is a lossy optimization and therefore explicit and testable.

A compaction summary should preserve:

- current user goal;
- accepted constraints/decisions;
- unresolved questions;
- current plan/changed files;
- important identifiers/errors;
- relevant approval outcomes;
- provenance/source event or message ranges.

A model-generated summary is never promoted to trusted instructions merely because it summarizes trusted content. It is a derived evidence object whose claims may need to be re-read from source for sensitive/ambiguous decisions.

Do not destructively replace raw durable conversation/task history with only the summary. Compaction changes the request view, not the historical record.

## 8. Prepared request snapshot

Prompt Runtime outputs an immutable prepared request before Provider Core starts an attempt. Conceptually:

```ts
interface PreparedModelRequest {
  semanticRequestId: string;
  requestFingerprint: string;
  taskId: string;
  runId: string;
  turnId: string;
  routePlanId: string;
  requestEnvelopeHash: string;
  instructionSnapshotHash: string;
  contextPackageId: string;
  contextPackageHash: string;
  toolCatalogHash: string;
  agentConfigSnapshotHash: string;
  messages: NormalizedMessage[];
  tools: NormalizedToolSchema[];
  responseSchema?: JsonSchema;
  attachments?: NormalizedAttachmentRef[];
  budget: PreparedBudget;
}
```

The fingerprint is derived from normalized semantic content/config references, not secrets, volatile timestamps, or opaque correlation IDs such as `taskId`/`runId`/`turnId`. Those IDs remain explicit fields for tracing but do not make two otherwise identical semantic requests hash differently. It supports diagnostics/reproducibility and detecting accidental mutation; it is not a security signature.

Once an attempt starts, do not mutate the prepared snapshot in place. Retry/fallback may bind the same snapshot to another compatible RoutePlan candidate, but provider/model selection lives in `modelAttemptId` metadata rather than by rewriting the prepared request. New user input, changed instructions, refreshed context, changed tool exposure or policy-sensitive configuration produces a new turn/prepared request.

## 9. Provider-neutral request semantics

The normalized message/content model must support text plus typed content references without embedding vendor DTOs. Attachments are referenced through app-owned normalized metadata; Provider Core decides how/if the selected candidate can encode them.

Provider-specific prompt-cache hints, previous-response/session handles, provider-native tool IDs, opaque replay-safe continuation blocks and transport metadata may be attached downstream as adapter metadata but cannot change logical instruction precedence or become the only copy of user-visible conversation state. Canonical tool request/result relations use application `toolCallId`; adapters own vendor-ID mapping.

Capability mismatch discovered after preparation returns a structured decision/error to routing; adapters do not silently drop required modalities/tools/schema constraints.

## 10. Diagnostics and privacy

Diagnostics may show:

- prepared request/fingerprint IDs;
- instruction/context/tool category sizes;
- selected source references;
- capability/degradation decisions;
- redaction state;
- budget/reserve summary.

Do not expose API keys, authorization headers, OS keychain material, hidden credentials, raw secret-valued environment variables, or hidden/private model reasoning.

Raw provider payload logging is off by default and, if ever enabled in development, must pass redaction and clearly warn about sensitive content.

## 11. Testing/evals

Maintain fixtures covering:

- instruction-layer ordering;
- retrieved prompt-injection text remaining untrusted;
- repository instruction files from restricted roots staying out of the trusted project layer;
- activated Product Skill revision identity/fingerprint changing when its immutable content revision changes, while source trust class/origin survives normalization;
- deterministic tool/context ordering and request fingerprint stability;
- request snapshot immutability once an attempt starts;
- deterministic budget overflow/drop order;
- compaction preserving active decisions/next step without becoming trusted instruction;
- tool-catalog relevance selection and hard mode constraints;
- provider capability mismatch;
- redaction in diagnostics;
- equivalent normalized request producing expected adapter semantics.

The bootstrap Phase 1 fake-provider path exercises this runtime rather than bypassing it.
