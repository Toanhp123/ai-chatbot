# Prompt Runtime Contract

## 1. Purpose

The prompt runtime turns trusted application instructions plus selected user/project context into a provider-neutral model request. It is a separate boundary from both the Context Engine (which finds/selects candidate context) and Provider adapters (which translate normalized semantics into vendor protocols).

This boundary exists to make instruction precedence, provenance, compaction, tool exposure, privacy and debugging explicit rather than hidden inside UI components or adapter-specific strings.

## 2. Responsibilities

The prompt runtime owns:

- normalized instruction/message assembly;
- trusted-vs-untrusted provenance labels;
- context ordering and token-budget enforcement with the Context Engine;
- relevant tool/schema exposure with the Tool Runtime/MCP catalog;
- conversation compaction/summarization inputs and metadata;
- safe diagnostic representation of the final normalized request;
- deterministic fixture support for tests/evals.

It does not own provider HTTP/WebSocket transport, tool execution/authorization, repository indexing, or durable secret storage.

## 3. Instruction layers

Represent instruction layers as typed data, not string concatenation scattered throughout the app. The normalized ordering is conceptually:

1. non-overridable application safety/policy and runtime invariants;
2. selected agent profile/system behavior;
3. project/workspace trusted instructions explicitly configured by the user;
4. relevant product Skill instructions explicitly installed/selected under the extension trust model;
5. task/user conversation messages;
6. retrieved files, web/MCP resources, memory and artifacts as **untrusted context** unless a specific trusted source contract says otherwise;
7. tool results as **untrusted observations**;
8. compacted historical summaries with provenance and source range metadata.

User content can legitimately change the requested task, but untrusted retrieved/tool/web content cannot promote itself into a higher instruction layer or override application permissions.

Provider adapters may map these normalized layers to provider-specific system/developer/user/content-part fields without changing their logical precedence.

## 4. Prompt injection and provenance

Every externally sourced context item should carry at least:

- source kind (`workspace_file`, `attachment`, `web`, `mcp_resource`, `tool_result`, `memory`, `summary`, ...);
- stable source reference/path/URI when available;
- trust classification;
- content hash/version where useful;
- selection reason/relevance score when generated by retrieval;
- size/token estimate;
- redaction state.

Treat instructions found inside repository files, web pages, issues, tool output, MCP resources, plugin descriptions, generated artifacts and training data as data unless they came through an explicitly trusted repository-instruction mechanism.

The runtime should frame retrieved content so the model can distinguish source material from authoritative instructions. Permission decisions remain deterministic application logic outside the model.

## 5. Tool exposure

Do not send every installed tool or MCP schema on every turn.

The Tool Runtime exposes a searchable catalog with name, safe description, origin, risk/capability metadata and compact input schema summary. A selector chooses a bounded relevant subset using deterministic task/mode constraints plus model-assisted ranking only when useful.

Always include tools explicitly required by the active workflow. Never hide a permission-sensitive consequence in tool descriptions; enforcement happens at execution time.

Record which tools were exposed for an agent step so failures can be reproduced.

## 6. Context budget

The request planner receives a model capability/context budget and reserves headroom for model output, tool calls/results and system instructions before packing repository/history context.

Budget categories should be inspectable, e.g.:

- trusted instructions;
- recent conversation turns;
- explicit user attachments/selections;
- retrieved project context;
- compacted history/memory;
- tool schemas;
- output reserve.

When over budget prefer task-aware dropping/compression over naive truncation. Preserve user-selected context, active edits/diffs, required tool results and recent conversational dependencies before low-signal retrieval.

## 7. Conversation compaction

Compaction is a lossy optimization and therefore must be explicit and testable.

A compaction summary should preserve:

- current user objective and constraints;
- decisions already accepted;
- files/entities changed or under discussion;
- tool outcomes/errors that remain relevant;
- open blockers/next step;
- citations/source references when practical.

Do not treat a generated summary as higher-trust than the source messages. Keep recent raw turns and critical approval/security events outside aggressive compaction.

Support deterministic thresholds/policies so tests can force compaction without huge fixtures.

## 8. Provider-neutral request model

Define normalized types for concepts such as:

- role/instruction layer;
- text/image/file/referenced-content parts;
- tool definitions and tool results;
- structured-output intent/schema;
- reasoning/effort hints when supported;
- sampling/generation controls;
- request metadata/correlation IDs;
- privacy/cache hints;
- max-output/token budget.

Capability negotiation decides whether a requested feature is supported, emulated safely, or rejected with an actionable normalized error. Do not silently discard semantically important settings.

## 9. Diagnostics and privacy

Developer diagnostics may show the **normalized** assembled request with sizes, selected sources/tools, capability decisions and redactions. Do not expose API keys, authorization headers, OS keychain material, hidden credentials, or secret-valued environment variables.

Raw provider payload logging is off by default and, if ever enabled in development, must pass redaction and clearly warn about sensitive content.

## 10. Testing/evals

Maintain fixtures covering:

- instruction-layer ordering;
- retrieved prompt-injection text remaining untrusted;
- deterministic budget overflow/drop order;
- compaction preserving active decisions/next step;
- tool-catalog relevance selection and hard mode constraints;
- provider capability mismatch;
- redaction in diagnostics;
- equivalent normalized request producing expected adapter semantics.

The bootstrap Phase 1 fake-provider path should exercise this runtime rather than bypass it.
