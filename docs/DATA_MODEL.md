# Data Model

## 1. Principles

- SQLite is local application state, accessed only through the Storage layer.
- Use migrations from day one.
- Core relational state is explicit; JSON is reserved for extensible metadata where schema churn is expected.
- Credentials are never stored as plaintext in ordinary tables.
- High-volume append-only event data has retention/compaction policy.
- Rebuildable indexes/caches are distinguishable from user-authored durable state.
- Durable runtime history must preserve enough identity/evidence to explain retries, fallbacks, approvals, tool side effects and interrupted runs.
- In-memory runtime objects are projections/caches; they do not become an independent source of truth.

## 2. Identity and IDs

Use stable opaque application IDs (UUID/ULID or similarly collision-safe identifiers) for durable entities. Provider IDs/model IDs remain external identifiers and are not primary keys.

Runtime correlation uses the hierarchy defined by `AGENT_RUNTIME.md`:

- task;
- run;
- turn;
- model attempt;
- tool call;
- tool attempt;
- approval request.

Provider request/session IDs are stored as provider-scoped metadata, never substituted for app IDs.

All major rows include timestamps and, where useful, schema/version/revision fields for extensible payloads. Mutable configuration/settings records should support optimistic revision/version checks where multiple windows/processes could race.

## 3. Core entities

### Providers

`providers`

- `id`
- `display_name`
- `protocol`
- `base_url`
- `auth_strategy`
- `secret_ref` nullable
- `config_json`
- `enabled`
- revision/version metadata
- `created_at`, `updated_at`

`provider_models`

- provider-local model ID;
- display metadata;
- capability snapshot;
- capability provenance/freshness/version metadata;
- source (`discovered`, `preset`, `manual`);
- user override metadata;
- last seen / health metadata.

`routes` / `route_candidates`

Ordered deterministic candidate list plus route policy and revision.

### Conversations

`conversations`

- project association optional;
- title/status;
- default route/model;
- timestamps/revision.

`messages`

- conversation ID;
- logical role/type;
- stable sequence/order;
- normalized content metadata;
- provenance/trust metadata where needed;
- task/run/turn correlation when generated by an agent;
- originating model-attempt/tool-call correlation when applicable;
- provider request correlation only as vendor-scoped metadata.

For agent-generated final content, the message row is the canonical durable product projection. The corresponding lifecycle event references its message ID; do not persist a second independent full message body in the event payload. When both are durable they commit consistently.

Large/binary attachment payloads should be file-backed with metadata references rather than arbitrary DB blobs unless measured otherwise.

`message_parts` may be used when content-part queries/versioning require normalization; do not introduce it until needed.

### Attachments, blobs and artifacts

`attachments`

- original file metadata;
- content hash;
- extraction status/version;
- cached extracted representation reference.

`artifacts` / `artifact_versions`

- type/title/project/conversation/task origin;
- versioned content/path/blob reference;
- export metadata;
- provenance.

Large immutable payloads may use a content-addressed local blob store rather than SQLite blobs. Blob metadata includes content hash, size, media type, storage version and reference/lifecycle state. Writes use temp-file + fsync/close as appropriate + atomic rename on the same filesystem before DB metadata commits to the final reference.

Garbage collection must prove a blob has no durable references before deletion. A missing blob is a typed integrity error, not empty content.

### Projects/workspaces

`projects`

- title/description/instructions;
- preferred route;
- settings/revision.

`workspaces`

- project association (a project may own multiple workspace roots);
- canonical path/root identity;
- Git/worktree metadata cache;
- trust state (`restricted`/`trusted`) plus trust source/revision/updated-at metadata;
- repository-instruction activation/approval metadata by canonical root/source where needed;
- index status;
- revision/last observed state.

Workspace mutation-lease records may be persisted or coordinated in-memory plus crash-reconciled, but the authoritative owner/run/root identity and expiry/release evidence must be inspectable while a lease exists.

### Tasks, runs, turns, attempts and events

`tasks`

- parent task optional;
- project/conversation;
- durable task status;
- goal/request metadata;
- timestamps.

`task_runs`

- task ID;
- prior run ID when this is an explicit resume/retry;
- agent configuration snapshot/reference;
- execution workspace/root reference;
- optional base revision/branch/worktree/lease metadata;
- route/configuration/policy snapshot/reference used to resolve per-turn RoutePlans;
- state;
- budget/deadline fields;
- start/finish/interruption reason;
- timestamps.

`turns`

- run ID;
- monotonic turn number;
- `PreparedModelRequest.semanticRequestId` + `requestFingerprint`;
- immutable route-plan snapshot/reference + plan fingerprint/request-envelope hash, sufficient to recover the candidate/capability versions used;
- context package ID/hash;
- tool catalog/config snapshot hashes;
- state/finish reason;
- timestamps.

`model_attempts`

- turn ID;
- monotonic attempt number;
- provider/model/route candidate;
- `PreparedModelRequest.requestFingerprint`;
- continuation strategy (`canonical_replay`, provider handle, or equivalent);
- provider request/session/response IDs and bounded opaque continuation-state reference where applicable;
- retry/fallback relationship/reason;
- commit-state marker (for example no output / output committed / tool request committed);
- terminal status/error class;
- usage/cost/latency fields;
- timestamps.

`task_events`

Append-oriented **durable lifecycle** events with unique `(task_id, sequence)` and bounded payloads. Sequence is monotonically allocated across the Task lifetime, including later Runs, so task-only events never need a fabricated `run_id` and resume history has one stable order. Run/turn/attempt/tool/approval correlation columns remain nullable/required according to event depth rather than being hidden only inside opaque JSON. High-frequency model text deltas/tool progress/stdout chunks are transient stream data and are not stored here by default; canonical final message snapshots (or explicitly marked committed partial-message evidence after interruption), tool results, and bounded diagnostic artifacts are the durable representation.

`tool_calls`

- task/run/turn/model-attempt correlation;
- application `toolCallId` plus provider-native tool-use ID/reference where applicable;
- tool ID/version/provenance;
- security-relevant causal instruction/extension source refs (for example active MCP-origin Skill revision) when policy-relevant;
- operation fingerprint;
- normalized arguments or safe hash/redacted representation;
- canonical resources/bound expected preconditions;
- idempotency/retry class;
- logical status/timestamps;
- result summary/error/unknown-outcome reference;
- permission decision / approval request ID;
- resulting resource version/hash where useful.

`tool_execution_attempts`

- tool call ID + monotonic attempt number / opaque `toolAttemptId`;
- execution adapter/backend identity;
- stable idempotency key reference when supported;
- dispatch-intent/dispatched/terminal timestamps or state markers;
- terminal success/failure/`unknown_outcome`/cancelled result;
- reconciliation evidence/reference when an ambiguous dispatch is inspected rather than replayed.

`approvals`

- approval request ID;
- task/run/tool call;
- operation fingerprint;
- bound causal instruction/extension source refs when they are part of the grant scope;
- normalized permission request/resource scope;
- decision/source;
- grant scope/expiry/session lifetime;
- stale/revoked/resolved state;
- timestamps.

### Context/indexes

`repository_indexes`

- workspace/root;
- index/artifact kind;
- index version;
- parser/indexer version;
- relevant ignore/config version;
- root/content snapshot metadata;
- status/error.

Detailed symbol/search indexes may live in dedicated SQLite tables or sidecar storage depending on measured access patterns. Rebuildable index records must be distinguishable from durable conversation/artifact data.

### Extensions

`skills` / `skill_revisions`

- app-owned Skill identity;
- source kind (`local`, `plugin`, `mcp`, ...), source URI/server revision where applicable;
- instruction trust class/provenance (for example local-reviewed vs MCP remote-untrusted) that survives normalization;
- immutable revision/content-manifest hash;
- frontmatter/metadata and file digests/references;
- content-bound review/verification references required by source type;
- verification/snapshot status;
- created/superseded timestamps.

Manifest-backed MCP-delivered Skills may become immutable local Product Skill revision snapshots after **explicit per-Skill activation approval bound to the MCP server revision + Skill URI + held manifest/frontmatter revision**, but they retain MCP remote-untrusted instruction provenance. A manifest/frontmatter/content-binding change creates a new review/activation surface rather than inheriting the prior approval. Dynamic or otherwise not content-bindable MCP content is not persistently activated as a durable Product Skill revision in V1; it remains ordinary origin-tagged untrusted MCP context.

`plugins` / `plugin_revisions`

- plugin identity;
- manifest/source/publisher/version;
- package/integrity fingerprint;
- declared contribution/capability summary;
- install/review state;
- superseded/rollback metadata.

Security-relevant update changes produce a new revision rather than overwriting the reviewed revision in place.

`mcp_servers` / `mcp_server_revisions`

- app-owned server identity and default/configuration scope;
- transport kind;
- canonical endpoint or structured stdio command/args/cwd fingerprint;
- bounded environment/secret-reference policy fingerprint;
- protocol/era/profile/extension capability snapshot;
- auth secret reference;
- review state;
- health/fetched-at metadata.

`extension_activations`

- contribution kind + immutable revision ID (`skill_revision`, `plugin_revision`, `mcp_server_revision`, ...);
- scope kind/ID (`global`, `project`, or other explicitly supported product scope);
- active/suspended/revoked state;
- review/activation approval reference and security-relevant trust snapshot;
- activated/revoked actor/source + timestamps.

One immutable revision may have multiple scoped activation records. Activation never mutates revision bytes/identity, and changing a security-relevant revision creates a new activation/review surface rather than rewriting the old record.

Tool/resource/prompt/Skill catalogs may be cached with TTL/cache-scope and schema/content fingerprints but remain server-derived untrusted metadata. Server self-reported name/version is display/diagnostic metadata, not identity.

`agents`

Configurable agent profile: instructions reference, route, tool/MCP exposure allowlists, Skill associations, permission-profile reference, turn/budget limits, revision. Exposure allowlists only narrow eligible descriptors; they are not extension activation or permission grants.

### Memory

`memories`

- scope global/project;
- content;
- source/provenance;
- enabled;
- timestamps/revision;
- optional confidence/metadata.

Memory mutations are explicit and auditable.

### Usage

`usage_records`

- PreparedModelRequest/task/run/turn/model-attempt/conversation/project associations;
- provider/model/route;
- token categories when available;
- latency/TTFT;
- cost/currency/source/pricing-version;
- raw provider usage metadata only if bounded and non-sensitive.

Failed/retried model attempts may incur cost and remain represented rather than being collapsed into only the successful attempt.

### Workspace checkpoints

`workspace_checkpoints`

- task/run/workspace;
- Git commit/tree/stash/reference where applicable;
- app-managed backup metadata where needed;
- changed files summary;
- restore status.

Use a distinct name from Model Lab training checkpoints; they are different concepts and retention rules.

### Local models

`local_runtimes`

- runtime type + canonical endpoint;
- endpoint class (`loopback`, `lan`, `remote`, `unknown`);
- process ownership (`external`, `app-managed`, `unknown`) and app-owned process identity when applicable;
- auth secret reference;
- management/capability snapshot with provenance/freshness;
- health/runtime revision metadata.

`local_models` / model revisions

- runtime/external ID plus stable app identity;
- source repository/artifact + immutable revision/digest where known;
- architecture/quantization/format/size/context/capabilities with provenance;
- tokenizer/template metadata where known;
- location/source/license/custom-code requirement;
- loaded state and fit estimates cache;
- integrity/verification metadata.

Mutable aliases such as `latest` are discovery metadata, not the sole durable model revision identity.

### Model Lab

Model Lab persistence follows ADR-0005. Do not store a mutable path/config blob as the entire experiment identity.

`datasets`

- logical user dataset identity/display metadata;
- current/reference relationships only; immutable content lives in revisions.

`dataset_revisions`

- source identity + content digests;
- canonical schema/version;
- stable record IDs;
- provenance/license metadata when known;
- validation/statistics;
- explicit transform lineage;
- split strategy/seed/membership digest;
- immutable revision digest.

Backend-specific tokenization/template/packing output is rebuildable prepared-data/cache state keyed by DatasetRevision plus tokenizer/template/truncation/packing/loss-mask implementation fingerprints. Do not silently mutate the DatasetRevision.

`training_plans`

- immutable plan schema/version + digest;
- base-model revision/digest;
- tokenizer/template identity;
- DatasetRevision + prepared-data fingerprint;
- backend/environment revision and capability snapshot;
- SFT/LoRA/QLoRA semantics and resolved hyperparameters;
- seed/determinism request;
- resource/device set;
- checkpoint/retention/output/network/tracking policy.

`training_jobs`

- user-visible logical experiment;
- TrainingPlan reference;
- display/status summary **derived from current/latest attempt and promotion state**, not a second authoritative execution state machine;
- created/updated timestamps.

`training_attempts`

- job/plan reference and parent/resume lineage;
- concrete worker/process identity;
- actual backend/environment/hardware snapshot;
- resource-lease identity;
- status/terminal reason;
- started/ended timestamps.

Retry/resume never overwrites a prior attempt.

`training_checkpoints`

- producing TrainingAttempt;
- checkpoint kind/completeness;
- resume-compatibility fingerprint;
- staged/finalized path;
- manifest/file integrity;
- trainer-state capabilities;
- retention/pin/reference state.

`model_artifact_revisions`

- kind (`adapter`, `merged-model`, other supported inference artifact);
- producing/import source + immutable lineage;
- base-model dependency when applicable;
- finalized path/size/checksums;
- format/quantization/license/provenance;
- load-validation status;
- Local Models registration/promotion state.

`evaluation_suite_revisions` / `evaluation_runs`

- immutable case/dataset + metric/evaluator identity;
- generation/template parameters and determinism metadata;
- evaluated base/candidate artifact revisions;
- aggregate metrics plus references to bounded per-case outputs;
- optional judge provenance when model-as-judge exists later.

`model_promotions`

- immutable Model Promotion Record ID;
- promoted ModelArtifactRevision + resulting Local Model/revision reference;
- EvaluationRun/TrainingPlan/DatasetRevision lineage references used for the decision;
- actor/source and timestamp;
- optional alias before/after references when promotion changes a user-facing alias;
- validation/load-smoke/license/provenance evidence references.

Promotion history is append-only. `model_artifact_revisions` may cache current registration/promotion summary for UI convenience, but that mutable summary is not the audit source of truth.

`training_metrics` stores structured sampled/coalesced metrics keyed by attempt/step. Large raw logs and per-case evaluation payloads belong in bounded artifact files with DB references rather than huge JSON cells.

## 4. Transaction and consistency invariants

Storage owns transaction boundaries for durable cross-row invariants.

At minimum:

- state projection + corresponding lifecycle event are committed atomically when both are durable; final message projection + its completion event follow the same rule;
- `(task_id, sequence)` is unique and monotonically allocated by Storage/application coordination across the Task lifetime, not UI arrival order; Run/deeper IDs provide correlation while task-only events remain naturally ordered without fabricated Runs;
- tool/approval records cannot reference non-existent task/run/turn rows; tool execution attempts cannot exist without their logical tool call;
- foreign-key enforcement is enabled and tested for owned relational data;
- a completed/failed/cancelled/interrupted run cannot later accept ordinary new turn/tool/approval execution events; pending approvals owned by such a Run become stale/closed;
- an approval resolution cannot mutate a different operation fingerprint than the one requested;
- a tool execution attempt that reached dispatch-intent but lacks trustworthy terminal evidence is never normalized to success/failure solely because of process restart; reconcile or preserve unknown outcome;
- optimistic revision checks reject stale settings/config writes instead of silently last-writer-wins where races matter;
- a TrainingAttempt cannot change its TrainingPlan identity after launch; retry/resume creates a new attempt;
- a TrainingCheckpoint/ModelArtifactRevision is promotable/resumable only after finalized manifest + integrity state commits; partial/staging output is never normalized to complete;
- every Local Models registration/promotion of a Model Lab artifact appends a Model Promotion Record referencing the immutable ModelArtifactRevision and supporting lineage/evaluation evidence; it cannot be implied solely by TrainingAttempt completion.

Do not hold a SQLite transaction open across provider/network/user-approval/tool subprocess waits. Persist intent/state, commit, perform external work, then persist the result/reconciliation in a new bounded transaction.

## 5. SQLite behavior

Evaluate WAL in Phase 0. Expected desktop pattern:

- one Storage service owns migration lifecycle and write coordination;
- short transactions;
- background readers permitted;
- busy handling is bounded/actionable rather than infinite;
- WAL checkpoint behavior/storage growth monitored if WAL is selected;
- graceful shutdown closes connections;
- database remains on local filesystem.

Do not place the primary DB on network-mounted storage and assume WAL semantics are safe.

Run lightweight integrity/foreign-key checks at appropriate recovery/support points, not on every hot-path transaction.

## 6. Migrations

Each schema change:

- has an ordered reproducible migration;
- runs transactionally where SQLite permits;
- includes forward data transformation;
- has backup/restore strategy for destructive transformations;
- is integration-tested from at least the previous supported schema version;
- updates this document when conceptual ownership changes.

Migration startup uses an explicit lock/single-owner mechanism so two app windows/processes cannot race the schema upgrade.

Avoid manual “fix production DB” instructions as the intended migration mechanism.

## 7. Retention and deletion

Potentially high-volume data requiring policy:

- durable task events and any optional transient trace buffers;
- tool output/log excerpts;
- provider diagnostics;
- repository indexes;
- training logs;
- artifact versions.

Retention should be configurable later but defaults prevent unbounded local growth.

Retention/deletion is referentially aware: do not delete an event/blob/artifact still required to explain an active task, restore a checkpoint, render a retained conversation, calculate retained usage, or satisfy audit policy. Prefer deleting rebuildable caches before durable user history.

Ordinary file/SQLite deletion is not guaranteed secure erasure on SSD/journaled filesystems; do not promise forensic secure deletion unless a platform-specific mechanism is explicitly implemented and tested.
